L'API est servie sous `/api`. Sa documentation OpenAPI interactive est disponible sur `/api/docs`. Les réponses sont en JSON (`Accept: application/json`) ou en JSON-LD (`application/ld+json`). Les `PATCH` attendent `Content-Type: application/merge-patch+json`.

## Utilisateur

```bash [Terminal]
curl -X POST https://mailer.exemple.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email": "alice@exemple.com", "password": "…"}'
# → { "token": "<jwt>" }
```

Le JWT est valable une heure et s'utilise avec `Authorization: Bearer <jwt>`. Les comptes LDAP se connectent avec leur mot de passe d'annuaire.

## Application

```http
Authorization: Bearer rpa_…
```

Seule, une application ne peut qu'appeler `GET /api/me`. Pour agir, elle **impersonne** un utilisateur :

```http
Authorization: Bearer rpa_…
X-Impersonate-User: alice@exemple.com
```

Elle obtient alors les droits de cet utilisateur, **sauf** le rôle administrateur. Cela suppose que l'application ait l'option « Peut agir en tant qu'utilisateur ».

## Composeur embarqué

```http
Authorization: Embed <jeton d'embed>
```

Réservé à l'iframe du composeur, avec une portée limitée. Voir [Sécurité du composeur](/embed/security#endpoints-accessibles-avec-un-jeton-dembed).

## Qui suis-je ?

```bash [Terminal]
curl https://mailer.exemple.com/api/me -H "Authorization: Bearer …" -H "Accept: application/json"
```

```json
{
  "user": { "id": "…", "email": "alice@exemple.com", "displayName": "Alice Durand" },
  "application": { "id": "…", "name": "CRM" },
  "roles": ["ROLE_USER", "ROLE_APPLICATION", "ROLE_IMPERSONATION"],
  "embed": false
}
```

`roles` contient les rôles **effectifs** de la requête : une application qui impersonne un administrateur n'y voit pas `ROLE_ADMIN`.
